## Sparklines not visible in the account sidebar

Account trend sparklines — the small charts next to account groups and individual account rows in the sidebar — did not render in some versions. The charts appeared blank even though the sparkline data had loaded correctly.

<AccordionGroup>
  <Accordion title="What caused this issue?">
    The chart controller that draws sparklines included a dimension guard that skipped rendering when the drawable width or height, after subtracting chart margins, was less than 50 pixels. Sidebar sparkline containers are 32×12 pixels (account group totals) and 32×20 pixels (individual account rows), so they fell below the threshold and were never drawn.
  </Accordion>

  <Accordion title="How was it fixed?">
    The dimension guard skips rendering when the drawable width or height is zero or negative after chart margins are subtracted. Small containers with positive drawable dimensions, including sidebar sparklines, render normally. A ResizeObserver redraws when layout changes give the chart usable dimensions.

    Charts whose drawable width and height were already at least 50 pixels are unaffected by this guard change.

    Upgrade to a build containing [Sure PR #4361](https://github.com/we-promise/sure/pull/4361). As of October 21, 2026, the fix is on `main` but is not in the latest stable release, `v0.7.5-hotfix.2`. No configuration change is required.
  </Accordion>
</AccordionGroup>

## AI-detected merchants were created as shared records

When merchant detection identified a new merchant from a transaction's description, Sure previously created a globally-shared `ProviderMerchant` record (source: `ai`). Because those records are visible to every family on the deployment, a transaction description crafted to steer the LLM's output could create or match a shared merchant with an attacker-chosen name, website, or logo — affecting all other families.

<AccordionGroup>
  <Accordion title="What was affected?">
    The `Family::AutoMerchantDetector` class, which runs as part of the background merchant detection job. When no existing merchant could be matched for a transaction, it fell back to creating a `ProviderMerchant` (source: `ai`) scoped globally rather than to the family.

    Reusing an already-existing shared merchant by website or name was not affected — that path does not write new data into shared records.
  </Accordion>

  <Accordion title="How was it fixed?">
    When AI detection cannot find a shared merchant to reuse, it now creates a `FamilyMerchant` scoped to the requesting family instead of a global `ProviderMerchant`. AI-sourced merchants from before this fix are also limited to the family that already has them on its transactions — they are no longer matched by name or URL across families.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Account name and balance visible to family members without access after a sync

In earlier versions, when an account finished syncing, Sure broadcast a rendered account row — including the account name and balance — on the family's shared Turbo stream. Every signed-in family member subscribed to that stream, including members who did not have access to the account. The row reached their browser after every sync even though the accounts page did not show it to them.

<AccordionGroup>
  <Accordion title="What was affected?">
    Any account that could sync independently — linked accounts (connected via a provider) and manual accounts that were synced — could expose their name and balance to all currently signed-in family members, regardless of whether those members had view or edit access to the account.
  </Accordion>

  <Accordion title="How was it fixed?">
    The broadcast that replaced the account row in the family stream is removed. Instead, when a sync completes, Sure sends a lightweight sync toast to each browser. The browser refreshes through its own authenticated request, so only members with access see the account data. Refresh can be deferred during interaction with forms or dialogs, and a manual refresh may be needed.

    The fix also covers linked accounts that sync on their own with no follow-up provider event, which would previously have left the accounts page stale for members who do have access.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Settings link causes a 500 error when many accounts are filtered

Opening the **Settings** link from a transactions list filtered by a large number of accounts could result in a 500 error (`CookieOverflow`). The transactions list passes the current page's full URL — including all selected account IDs — as a `?return_to=` query parameter so Sure can return you to the same filtered view after you leave settings. With enough accounts selected, that URL exceeds the 4 KB limit of the cookie-backed session.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    Sure stores the `?return_to=` value in the session so it can redirect back to the page you came from after completing an action in settings. The session is stored entirely in an encrypted browser cookie. When the `return_to` URL contains dozens of account IDs as query parameters, the resulting cookie size exceeds 4 KB and Rails raises a `CookieOverflow` error, producing a 500 response.
  </Accordion>

  <Accordion title="How was it fixed?">
    When the `return_to` value exceeds 1 KB, Sure now stores only the path without its query string. If even the bare path is over 1 KB, the `return_to` value is discarded entirely and the previous stored value is also cleared so a stale redirect target is never used. When the shortened path fits, Sure retains it as the return destination without the filters. Only when the path is discarded does Sure fall back to the default destination.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## "All" chart period starts later than expected

When you select the **All** period on a net worth or account chart, the chart now starts one month before the earliest Transaction or Trade entry across your family — not your earliest entry of any kind.

In earlier versions, Sure used the oldest entry of any type to anchor the All period. A single valuation or opening balance dated years in the past stretched every All-range chart back to that date, leaving a long flat line with no activity before any real spending or trading began.

<AccordionGroup>
  <Accordion title="What changed?">
    The All period now anchors to one month before the first Transaction or Trade entry across your family. Valuations and opening balances no longer affect how far back the All range extends.

    If your family has only valuations and no Transactions or Trades, the All period uses the family’s oldest entry date when it is before today; a missing, today, or future start falls back to five years ago.
  </Accordion>

  <Accordion title="Why does my chart look different after upgrading?">
    If you had a valuation or opening balance dated further back than your first real transaction, the All chart will now start later. The data is unchanged — only the visible range has shifted to focus on the period where you have actual activity.

    Budgets and the AI balance sheet are not affected. They still use the oldest entry date as before.
  </Accordion>
</AccordionGroup>

## Mixed-currency arithmetic produces wrong totals silently

Earlier versions of Sure allowed arithmetic operations (`+`, `-`, `/`, `<=>`) between `Money` objects in different currencies. The result kept the left operand's currency and discarded the right operand's — so `200 USD - 180 EUR` returned `20 USD` with no error or log line. This affected syncs, transfer matching, insight generators, and some report pages for families that hold accounts in more than one currency.

<AccordionGroup>
  <Accordion title="What was affected?">
    Any calculation that combined two `Money` values from different currencies without an explicit `exchange_to` conversion first. Common surfaces include:

    - Balance and net worth totals across multi-currency accounts
    - Transfer matching when accounts are in different currencies
    - Insight generators and assistant read functions
    - Report and API responses for families mixing currencies such as EUR, GBP, and USD
  </Accordion>

  <Accordion title="How was it fixed?">
    `Money` arithmetic now checks that both operands share the same currency before proceeding.

    In development and test, a mismatch raises `Money::CurrencyMismatchError` immediately so the call site is easy to find.

    In production, the mismatch is reported through `Rails.error` and logged at `warn` level (deduplicated by operation, currency pair, and call site within a bounded per-process cache) and the operation keeps its previous result so no page starts failing while the root cause is fixed. Equality comparisons between different currencies return false without raising.

    Versions containing currency-mismatch detection enable it without an additional configuration change.
  </Accordion>

  <Accordion title="I see a currency mismatch warning in my logs — what do I do?">
    A log line like `[Money] Can't apply + to USD and EUR amounts; convert one with exchange_to first` means Sure found a call site that combines amounts in two different currencies without converting first.

    The log includes the call site location. In most cases the fix is to call `exchange_to` on one of the amounts before the operation, passing the target currency and the relevant date.

    If you are self-hosting a customized version of Sure, search for the call site identified in the log and add the conversion. On an unmodified install, upgrade to the latest release — the known call sites are being fixed progressively.
  </Accordion>
</AccordionGroup>

## Confirmation dialogs could run script from bank-provided names

In earlier versions, confirmation dialogs (such as those shown when deleting a provider merchant, resetting holdings, or replacing a SimpleFIN account) interpolated user-supplied names directly into the dialog body via `innerHTML`. Names sourced from bank feeds, brokerage providers, or other family members could contain HTML that the browser executed as script.

Because provider merchant rows are shared across families, a crafted merchant name could reach any user who opened a confirmation involving that merchant.

<AccordionGroup>
  <Accordion title="What was affected?">
    Confirmation dialogs that showed a record name in the body text, including:

    - Provider merchant deletion confirmations (the merchant name came from bank feeds and was shared across families)
    - SimpleFIN account replacement prompts (account name from the bank)
    - SnapTrade brokerage and holdings reset confirmations (brokerage name and ticker symbols from the provider)
    - Any other confirmation built through `CustomConfirm` or the raw `turbo_confirm` hash that included a record name
  </Accordion>

  <Accordion title="How was it fixed?">
    The confirmation dialog now sets its body using `textContent` instead of `innerHTML`. Record names are rendered as plain text regardless of how the confirmation was constructed, so HTML in a name is never parsed or executed.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## MXN amounts show wrong number separators in Spanish

When the interface language is set to Spanish, Mexican peso (MXN) amounts were formatted using European-style separators — a comma as the decimal separator and a dot as the thousands separator. This produced values like `1.234,56 MXN` instead of the correct `1,234.56 MXN`.

<AccordionGroup>
  <Accordion title="What caused this issue?">
    Sure formats currency amounts using the active locale's separator rules. Spanish uses European-style separators for most currencies, but MXN natively uses US-style separators (dot as decimal, comma as thousands). The formatter did not have a currency-specific override for MXN under the Spanish locale, so it applied the locale's default separators instead.
  </Accordion>

  <Accordion title="How was it fixed?">
    The number formatter now checks the currency code before applying locale-derived separators. When the currency is MXN and the active locale is Spanish, Sure retains MXN’s dot decimal separator and comma thousands separator. Other locales keep their existing formatting rules. All other currencies continue to follow the locale's own separator conventions.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Category avatar preview does not update when picking a color

When editing or creating a category, changing the color using the color picker previously did not update the avatar preview — the icon and background appeared to stay at the original color until the form was saved.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    The category avatar uses a `--avatar-color` CSS variable to compute both the background (a light tint) and the icon color (the full color). Earlier versions of the color picker updated the avatar's inline `style.color` and `style.backgroundColor` directly instead of setting the variable. Overriding the resolved values bypassed the theme-aware `color-mix` logic, so the preview stayed stuck at the last saved color.
  </Accordion>

  <Accordion title="How was it fixed?">
    The color picker now updates the `--avatar-color` CSS variable on the avatar element when you select a new color. The avatar's CSS reads from the variable, so both the background tint and the icon color update immediately as you pick.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Account balance or net worth drops to zero unexpectedly

If an account balance or your net worth chart falls to zero for a day — without any transactions that explain it — a provider may have returned a zero or invalid exchange rate for that currency pair on that date. Storing a zero rate converts every balance in that currency to zero.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    Exchange rate providers occasionally return a zero rate for a single-day lookup. Earlier versions of Sure stored whatever value the provider returned. Any conversion that used that rate multiplied the balance by zero, wiping the reported value for that day. The bulk importer was already protected, but single-rate lookups were not.
  </Accordion>

  <Accordion title="How was it fixed?">
    Sure now validates every rate — whether from a single lookup or a series — before storing it. A finite, positive number is required. Rates that are zero, negative, `NaN`, or infinite are rejected:

    - A single-rate lookup that returns an unusable value is treated as a failed response; that response supplies no replacement rate. Any fallback depends on the caller.
    - Rates in a bulk series that are unusable are dropped. The importer can fill subsequent gaps from a usable prior rate. Without an earlier anchor it begins at the earliest usable provider date; if no usable rates are returned, it does not fill the series.
    - A database check constraint rejects zero, negative, and non-finite values for any write that bypasses model validations, such as bulk upserts.
    - Any provider rate rejected by this validation is recorded in **Settings → Debug** under the `exchange_rates` category so you can see which provider returned the bad value and on which date.

    A rate of exactly `1` is valid and is stored normally (used for pegged currencies).

    Existing invalid rates in the database are removed when you upgrade. The next sync refetches those dates from the provider.

    Versions containing this validation need no configuration change to enable it.
  </Accordion>

  <Accordion title="How do I confirm the cause?">
    Go to **Settings → Debug** and filter by the `exchange_rates` category. Entries naming the concrete exchange-rate provider class, with level `warn`, show the provider name, the currency pair, and the invalid rate that was rejected.
  </Accordion>
</AccordionGroup>

## Account shows an error when a foreign-currency transaction has no exchange rate

If an account holds transactions in a currency that has no exchange rate available for a given date, earlier versions would abort the entire balance calculation for that account, marking it as errored even though all transactions had imported correctly.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    Balance calculation converts each entry into the account's base currency. When no exchange rate exists for the currency pair on a specific date, Sure previously raised an error that escaped the calculation loop. A single unconvertible entry was enough to produce no balances at all and leave the account in an error state.
  </Accordion>

  <Accordion title="How was it fixed?">
    Sure now skips the unconvertible entry rather than aborting. The entry is excluded from the balance total, the missing rate pair is written to **Settings → Debug** under the `sync` category, and the rest of the account's transactions are still used to calculate balances normally.

    Holdings with a missing rate are handled differently: they are still counted toward the total at a 1:1 rate (to avoid phantom cash appearing in the cash balance), and the occurrence is also logged.

    To see which rate was absent, go to **Settings → Debug** and filter by the `sync` category. Look for entries from `Balance::SyncCache` with level `warn`.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>

  <Accordion title="How do I resolve the missing exchange rate?">
    Go to **Settings → Self-Hosting** and confirm an exchange rate provider is configured. Twelve Data is the default. After configuring or re-enabling a provider, trigger a manual sync on the affected account. Once rates are fetched, the previously skipped entries will be included in the next balance calculation.
  </Accordion>
</AccordionGroup>

## Dragging a section on the reports page activates mid-scroll on mobile

On mobile, a brief pause while scrolling the reports page could accidentally activate drag mode on a reorderable section, visibly shifting the section and interrupting the scroll.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    The reports page lets you reorder sections by deliberately holding a section and dragging. The previous hold delay was 150ms with no movement threshold, so a normal scroll gesture — a short pause followed by a swipe — was enough to trigger drag mode mid-scroll. Once drag mode activated, the section moved with the finger instead of the page scrolling.
  </Accordion>

  <Accordion title="How was it fixed?">
    The hold delay is raised to 800ms and a 10-pixel movement threshold is added. If the touch moves more than 10px before the hold delay expires, the pending drag is cancelled and native scrolling continues uninterrupted. A `touchcancel` event (for example, from an interrupting system gesture) now also discards the pending reorder instead of committing it.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Every click on the reports page navigates to a transaction drill-down in Safari

In Safari, clicking anywhere on the reports page — including the period picker or other controls — could unexpectedly navigate to a category's transactions drill-down instead of performing the intended action. On iOS Safari, the same layout also caused scrolling to freeze for the entire page.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    The earlier category-row implementation used an absolutely positioned stretched-link overlay. The fix addresses Safari reports of that overlay intercepting clicks outside the intended cells and iOS scrolling freezing. The current source also documents WebKit table-layout scroll-height problems with positioned overlays.

  <Accordion title="How was it fixed?">
    The stretched-link overlay is replaced with normal-flow `<a>` elements wrapping the icon, name, and entry count in the category cell, and separate `<a>` elements to the same destination in the amount and percentage cells. The clickable cells no longer rely on a positioned overlay anchored to a table row.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>

## Debugging rule failures

When an async rule run fails (for example, during a family sync or after a provider webhook), the error is written to the debug log. To view it:

1. Go to **Settings → Debug**
2. Filter by the `rules` category

Each entry includes the error message and the rule that failed. This is useful for diagnosing why auto-categorization stopped working after a provider or model change.

## When Rules Are Triggered

Rules run automatically during family syncs or can be triggered manually. Understanding when rules execute helps troubleshoot categorization issues.

<AccordionGroup>
  <Accordion title="Manual trigger (user-initiated)">
    Rules can be manually triggered in the following ways:
    
    - Clicking "Re-apply" on an individual rule in `/settings/rules`
    - Clicking "Apply All" in `/settings/rules`
    - Running the rake task: `bin/rails rules:apply_all[family_id]`
  </Accordion>
  
  <Accordion title="During family sync (only active rules)">
    Rules with `active: true` run automatically when a family sync occurs (`Family::Syncer.perform_sync`):
    
    **Scheduled syncs:**
    - `SyncAllJob` - runs daily at 2:22 AM for all families
    - `SyncHourlyJob` - runs every hour (for items that opt-in to hourly syncing)
    
    **Triggered syncs:**
    - Provider webhooks (Plaid, etc.) - triggers sync which eventually propagates to family
    - Manual sync button on accounts page
    - After CSV imports complete (`Import` model calls `family.sync_later`)
  </Accordion>
  
  <Accordion title="When rules do NOT run">
    Rules are **not** triggered in these scenarios:
    
    - **Manual transaction creation** - Only triggers an Account sync (not Family sync)
    - **Manual transaction editing (balance-affecting fields)** - Changing the amount, date, or account triggers an Account sync (not Family sync). Editing only descriptive fields — name, notes, category, merchant, or tags — does not trigger any account sync. Reports and budgets still pick up the change through the entries cache version bumped by the save.
    - **Inactive rules (automatic syncs)** - Rules with `active: false` never run during automatic family syncs

    **Apply All** is an exception: it runs all rules, active and inactive, so their transaction changes (category, merchant, tags, and so on) apply. Inactive rules skip the email notification action only. Matches seen while a rule is off stay unrecorded; they are handled when the rule is switched back on.
  </Accordion>

  <Accordion title="How do I see why a rule run failed?">
    Failures during async rule runs (including auto-categorize provider failures) are written to the debug log. To view them:

    1. Go to **Settings** → **Debug**
    2. Look for entries with category **`rules`**

    Each failed run includes the error message and the rule that triggered it.
  </Accordion>
</AccordionGroup>

## Category Rule Popup Behavior

When you select a category for a transaction, a prompt appears to create an automatic categorization rule. This prompt has two controls:

- **X (close)** — removes this individual prompt only. It makes no server call and does not affect future prompts.
- **Hide for today** — hides all rule suggestion prompts for 24 hours. A note below the buttons reads "Hide for today pauses these suggestions for 24 hours." so the behavior is always visible.

There is also a **Don't show this again** checkbox that permanently disables rule prompts for your account.

The prompt is gated by several conditions:

<AccordionGroup>
  <Accordion title="When does the prompt appear?">
    The prompt only shows when **all** of these conditions are met:

    1. You have not disabled rule prompts (`rule_prompts_disabled` is false)
    2. You have not clicked **Hide for today** in the last **24 hours**
    3. The transaction category actually changed
    4. No active transaction rule that sets this category already matches this specific transaction
    5. The transaction has a category assigned
  </Accordion>

  <Accordion title="Why isn't the prompt showing?">
    Check these common reasons:

    - **Recently snoozed**: You clicked **Hide for today** — wait 24 hours for prompts to resume
    - **A matching rule already exists**: An active rule whose conditions match this transaction already sets this category. A rule that sets the same category but whose conditions do not match this transaction does not suppress the prompt.
    - **Prompts disabled**: Check if `rule_prompts_disabled` is enabled for your account (set via **Don't show this again**)
    - **Prompt appeared behind an open drawer**: In older versions, the prompt could be rendered while the transaction drawer was still open. The browser renders native dialogs in a top layer above all other content, so the prompt sat behind the drawer unseen. A page refresh then removed it before the drawer closed. This is fixed in the current release — the prompt now waits until the drawer closes before appearing.
  </Accordion>
</AccordionGroup>

## Sure Doesn’t Work Over HTTPS

If Sure behaves incorrectly or fails when accessed over HTTPS, it’s usually due to missing SSL-related configuration between Nginx and Rails.

<AccordionGroup>

  <Accordion title="What causes this issue?">

    Sure relies on correct protocol headers to determine whether a request is secure.  
    When HTTPS is terminated at Nginx but not properly forwarded to the app, Rails may treat requests as HTTP.

  </Accordion>

  <Accordion title="How do I fix it?">

    Apply the following configuration changes:

    1. **Nginx**

       Ensure HTTPS is forwarded to the upstream app:

       ```nginx
       proxy_set_header X-Forwarded-Proto https;
       ```

    2. **docker-compose.yml**

       In the `x-rails-env: &rails_env` section, set:

       ```yaml
       RAILS_ASSUME_SSL: "true"
       ```

       This tells Rails to treat all requests as HTTPS.

  </Accordion>

</AccordionGroup>


## Some pages break over HTTPS

Sure uses WebSockets for certain pages. If some pages fail to render correctly or break entirely, this is often caused by missing SSL or upgrade headers in your reverse proxy configuration.

<AccordionGroup>

  <Accordion title="What are the symptoms?">

    You may see pages partially load, fail completely, or errors similar to:

    ```text
    Failed to upgrade to WebSocket (REQUEST_METHOD: GET, HTTP_CONNECTION: close, HTTP_UPGRADE: )
    ```

    This indicates that the WebSocket upgrade request is not being forwarded correctly.

  </Accordion>

  <Accordion title="How do I fix it?">

    Ensure your Nginx configuration includes the required WebSocket headers:

    ```nginx
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    ```

    These headers allow Nginx to properly handle WebSocket upgrade requests over HTTPS.

  </Accordion>

</AccordionGroup>

## Money In / Out links return 500 errors behind a forward-auth proxy

Self-hosted setups using a forward-auth proxy (Authelia, Authentik, Traefik forward-auth, etc.) may see 500 errors when clicking the **Income** or **Expense** drill-down links on the dashboard's Money In / Out widget. The links work fine when accessed directly.

<AccordionGroup>

  <Accordion title="What causes this issue?">

    The drill-down links previously included every accessible account ID as explicit query parameters. With many accounts, the resulting URL could exceed several thousand characters. Forward-auth proxies forward the full URL to the auth service in a request header; if that header exceeds the proxy's read-buffer or header-size limit, the request fails with a 500 before it reaches Sure.

  </Accordion>

  <Accordion title="How was it fixed?">

    Sure now omits the `account_ids` parameter when the widget's selected accounts exactly match the user's full set of accessible accounts — the same default the transactions page uses when no filter is applied. The result is identical, but the URL stays short.

    When a family has accounts excluded from reports or tax-advantaged accounts (so the eligible set differs from the accessible set), the IDs remain explicit to preserve the correct scope.

    Upgrade to the latest release to get this fix. No configuration change is required.

  </Accordion>

  <Accordion title="Workaround for older versions">

    If you cannot upgrade immediately, increase the header buffer size in your proxy. For Nginx acting as a forward-auth proxy:

    ```nginx
    proxy_buffer_size 16k;
    proxy_buffers 4 16k;
    ```

    For Traefik, set `forwardAuth.tls.insecureSkipVerify` is unrelated — instead configure your auth service to accept larger headers.

  </Accordion>

</AccordionGroup>

## Holdings list is slow with many securities

When an investment account holds a large number of securities, opening the holdings list in the web app could be noticeably slow in earlier versions.

<AccordionGroup>
  <Accordion title="What caused this issue?">
    The holdings list loaded each holding's associated security in a separate database query — one query per row. With many holdings, this produced a large burst of queries, causing the page to load slowly.
  </Accordion>

  <Accordion title="How was it fixed?">
    The holdings controller now fetches all securities for the current account's holdings in a single query before rendering the list. This replaces the per-row security lookups with eager loading, reducing the number of database queries needed to render the list.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Rule prompt disappears after changing category from the transaction drawer

In older versions, changing a transaction's category from the transaction detail drawer did not show the "create a rule?" prompt. The prompt was delivered while the drawer was still open, which placed it behind the drawer in the browser's rendering stack where it could not be seen or clicked. A sync completing shortly after then refreshed the page and removed it entirely.

<AccordionGroup>
  <Accordion title="What caused this issue?">
    The transaction drawer uses a native browser `<dialog>` element, which the browser places in a special top layer above all other page content. The rule prompt was streamed into the notification tray at the same time as the drawer was open. Because the notification tray sits below the top layer, the prompt was invisible and unclickable. When the next sync completed and morphed the page, the prompt was removed before the drawer ever closed.
  </Accordion>

  <Accordion title="How was it fixed?">
    The notification tray now defers streams targeting the prompt area and page-refresh streams while a dialog is open. Other streams continue normally. Once the last dialog closes, deferred prompts render first. A deferred refresh is skipped while a prompt is visible, preventing these background refreshes from erasing an unread prompt.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>
</AccordionGroup>

## Account disappears after a failed delete

If you delete an account and it vanishes from every list and the balance sheet but is never actually removed, one possible cause is that the background deletion job was not queued successfully. A job that fails during destruction is a separate case, described below.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    Deleting an account marks it `pending_deletion` and queues a background job to remove it. In earlier versions, the status was committed to the database before the job was pushed to the queue. If the job push failed at that point — because the queue (Redis) was temporarily unreachable or the push was rejected — the account was left marked `pending_deletion` with no job coming to finish the deletion. Because `pending_deletion` accounts are excluded from every visible list, the account appeared to vanish. There was no AASM event to leave `pending_deletion`, so you could not retry from the UI.
  </Accordion>

  <Accordion title="How was it fixed?">
    Sure now restores the account's previous status when the job push fails, so the account reappears in your list instead of staying hidden. The deletion attempt also runs under a row lock to prevent a double-submit from capturing a stale status. If the push was rejected, a failure alert is shown and you can try again once the queue is healthy.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>

  <Accordion title="What should I do if an account is already stuck?">
    If an account is already stuck in `pending_deletion` on an older version, verify that your worker container and Redis are healthy:

    ```bash
    docker compose ps worker
    docker compose logs worker --tail 50
    ```

    Once the worker is running and Redis is reachable, a server administrator can reset the account's status directly in the database, then attempt the deletion again from the UI.
  </Accordion>
</AccordionGroup>

## Account reappears as disabled after a failed deletion

When you delete an account, Sure marks it as pending deletion and then runs a background job to remove it. If the background job encounters an error during destruction, the account is restored to disabled so it reappears in your account list and can be deleted again.

<AccordionGroup>
  <Accordion title="What causes a deletion to fail?">
    Common causes include a database constraint violation, a callback on a related record raising an error, or a database deadlock (for example, a sync writing to the same account at the same time as the deletion).
  </Accordion>

  <Accordion title="How does Sure handle the failure?">
    When destruction fails, the background job restores the account to `disabled` so it becomes visible and re-deletable. The restore writes `status` and `disabled_at` directly — bypassing validations — and only updates the row if the status has not been changed by another process in the meantime, so a concurrent re-enable is never overwritten.

    For deadlocks specifically, Sure retries the deletion up to five times with growing waits (roughly 3 s, 18 s, 83 s, 258 s). The account stays in pending deletion during those retries. If all retries are exhausted, the account is restored to disabled.

    Every failed attempt is logged to **Settings → Debug** under the `background_jobs` category. Each entry includes the error class and message so you can see why the deletion failed.

    For accounts that were already disabled before deletion was attempted, the original `disabled_at` timestamp is preserved so the net worth chart cutoff is not moved forward to the failure date.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>

  <Accordion title="What should I do if an account is already stuck?">
    If an account is already stuck in pending deletion on an older version, it requires a direct database update to restore it. Set the account's `status` column back to `disabled` so it becomes visible and can be re-deleted from the UI. After upgrading, an exception raised during destruction restores the account to disabled automatically.
  </Accordion>

  <Accordion title="How do I see why the deletion failed?">
    Go to **Settings → Debug** and filter by the `background_jobs` category. Look for `error`-level entries with a message starting with `Failed to delete Account`. Each entry includes the error class, a truncated error message, and context about the record and family.
  </Accordion>
</AccordionGroup>

## Transactions disappear from income, spending, or budgets after a provider sync

If one or more transactions vanish from your income, spending, or budget totals after a sync — without being deleted — one possible cause in older versions is a provider removing a transaction that was part of a confirmed transfer.

<AccordionGroup>
  <Accordion title="What causes this issue?">
    A confirmed transfer links two transactions and assigns transfer-specific kinds such as `cc_payment` or `funds_movement`. A pending match leaves the existing kinds unchanged. When a provider removes a pending transaction that is one leg of a transfer, the transfer itself is destroyed. In older versions, deleting a transfer through that cascade path skipped the step that resets the surviving transaction's kind back to a standard value. The surviving transaction kept its transfer kind — `cc_payment` or `funds_movement` — with no transfer behind it, which caused it to be silently excluded from income, spending, and budget calculations.

    One possible trigger involves pending transactions from provider feeds: a provider may post a pending charge, the transfer is confirmed in Sure, and then the provider cancels or replaces the pending entry before it settles.
  </Accordion>

  <Accordion title="How was it fixed?">
    The kind reset now runs as a `before_destroy` callback on the transfer, so every deletion path — including cascades triggered by deleting a transaction or its entry — resets the surviving leg's kind to the appropriate standard value. Pending transfers keep their existing behaviour and are not affected.

    Upgrade to the latest release to get this fix. No configuration change is required.
  </Accordion>

  <Accordion title="What should I do if transactions are already missing?">
    The callback prevents this problem when a transfer is deleted; it does not repair transactions orphaned before the upgrade. A manual sync is not a general repair for those records. Ask your server administrator to investigate the affected transactions and correct their kinds only after confirming they are no longer transfers.

    To find potentially affected transactions, look for transactions with no linked transfer that have a kind of `cc_payment` or `funds_movement` on accounts where those kinds are unexpected.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="What causes this issue?">

The cache key for family reports is driven by the `updated_at` timestamp of the most recently changed entry. Because `update_all` bypassed callbacks, the entry timestamps were never updated, so the report cache key did not change and the old category data remained visible.

    The entry touch is batched in groups of 5,000 to avoid building an unbounded `UPDATE` statement on large merges.

## Chat shows "assistant not available" before the model finishes

Self-hosted users running a local model (Ollama, LM Studio, etc.) may see the chat fail with "assistant not available" even though the model is still generating a reply and tokens are being billed.

<AccordionGroup>

  <Accordion title="What causes this?">

    Sure uses a whole-turn watchdog (`AI_RESPONSE_TIMEOUT`, default 90 seconds) that starts when the message is queued. Custom OpenAI-compatible providers use a synchronous code path — nothing renders until the full reply is generated — so the watchdog fires before the model finishes.

    Tool-using turns make this worse: each tool call adds another full model round. The total time the watchdog must cover is:

    ```text
    (1 + ASSISTANT_MAX_TOOL_CALL_ITERATIONS) × OPENAI_REQUEST_TIMEOUT
      + tool execution time + queue wait
    ```

    With the defaults (`ASSISTANT_MAX_TOOL_CALL_ITERATIONS=8`, `OPENAI_REQUEST_TIMEOUT=60`), a worst-case turn can take up to 540 seconds of model time — far beyond the 90-second default.

  </Accordion>

  <Accordion title="How do I fix it?">

    The most effective approach is to lower `ASSISTANT_MAX_TOOL_CALL_ITERATIONS` (reducing the worst-case bound) and then size `AI_RESPONSE_TIMEOUT` using the formula above.

    For a local Ollama setup:

    ```bash
    OPENAI_REQUEST_TIMEOUT=300
    ASSISTANT_MAX_TOOL_CALL_ITERATIONS=2
    AI_RESPONSE_TIMEOUT=1200
    ```

    You can also set **Chat Response Timeout** from **Settings → Self-Hosting → AI Provider** in the UI. The environment variable takes precedence.

    See [Chat response timeout](/llm-support#chat-response-timeout) for full sizing guidance.

  </Accordion>

</AccordionGroup>

When a fresh family is created, Sure seeds it with a default set of categories. Importing a Sure export from another instance into that family previously failed preflight if any exported Category, Tag, or Merchant names matched the existing defaults.

<AccordionGroup>
  <Accordion title="What changed?">
    Name collisions on family-owned taxonomy records (Category, Tag, and family Merchant) are now preflight warnings rather than blocking errors. Sure reuses the existing record and updates it with the imported data. The confirm screen lists how many records were reused.
  </Accordion>

  <Accordion title="Will my data be correct after the import?">
    Yes. Transactions and rules that referenced the imported category or tag are remapped to the surviving (reused) record. The imported data updates that record's fields. No manual cleanup is needed.
  </Accordion>
</AccordionGroup>

## Balance anchor dated away from provider holdings

When Sure syncs an investment or crypto account, it compares the date of the balance anchor (the recorded current balance) with the date of the newest holding that the provider reported. If the two dates differ, Sure writes a warning to the debug log so you can investigate possible date-related cash artifacts in balance calculations.

<AccordionGroup>
  <Accordion title="What causes this warning?">
    Some providers date their holdings to the day the data was produced (for example, the previous trading day's close), while the balance anchor is set to the day of the sync. A gap between the anchor date and the holdings date can cause the reverse balance calculator to interpret differences in valuation as cash.

    Interactive Brokers and Plaid are known examples of providers that can produce this gap.

    Manual accounts, accounts without a current balance anchor, and accounts whose holdings carry no provider attribution are not checked and will never produce this warning.
  </Accordion>

  <Accordion title="Where do I see the warning?">
    Go to **Settings → Debug** and filter by the `provider_sync` category. Look for `warn`-level entries with a message like:

    ```
    Balance anchor dated 1 day(s) after the newest provider holding
    ```

    Each entry includes the provider, the account, both dates, and the gap in days as structured metadata. A steady gap does not add a new entry on each sync — only a change in the gap (including the gap closing) is recorded.

    When the gap closes, Sure logs an `info`-level entry:

    ```
    Balance anchor and newest provider holding are dated alike again
    ```
  </Accordion>

  <Accordion title="What should I do about it?">
    This warning is informational for self-hosted operators. The warning itself does not change account data. Investigate it if the account balance or cash history looks wrong.

    If you see cash appearing and disappearing in an investment account's balance chart on a one-day cycle, check **Settings → Debug** for a `provider_sync` warning on that account. The gap days value confirms a date mismatch, which may help explain the anomaly; it does not by itself prove the cause.

    The warning does not indicate a sync failure. The sync completes normally; only the debug entry is written.
  </Accordion>
</AccordionGroup>

## Auto mode does not retry with a simpler format after a malformed response

In older builds, `LLM_JSON_MODE=auto` only fell back to `none` mode when the provider rejected the request outright (HTTP 400) or returned more than 50% null results. A response that came back with HTTP 200 but contained unparseable or wrongly-shaped JSON escaped the fallback entirely, so `auto` behaved the same as `strict` for those models.

<AccordionGroup>
  <Accordion title="What caused this?">
    The auto-mode fallback caught `Faraday::BadRequestError` (HTTP 400) and the null-result threshold. JSON parse failures and shape mismatches raised a different error class that was not caught inside the auto-mode wrapper, so they propagated out and prevented the `none`-mode retry.

    For merchant detection specifically, the retry heuristic only counted a missing `business_name` as a failure. A result that had a name but no URL was treated as successful and suppressed the retry, even though Sure ignores detections without both fields.
  </Accordion>

  <Accordion title="How was it fixed?">
    A dedicated `ResponseFormatError` is now raised for JSON parse failures and shape mismatches in the generic extractors. The auto-mode wrappers for both categorization and merchant detection catch this error and retry once with `none` mode, the same as they already did for the >50% failure heuristic.

    The merchant-detection heuristic was also corrected: an item missing either `business_name` or `business_url` now counts as a failure for the retry threshold.

    Upgrade to a build containing [Sure PR #3602](https://github.com/we-promise/sure/pull/3602). No configuration change is required. If you were using `LLM_JSON_MODE=strict` as a workaround, switch to `auto`.
  </Accordion>
</AccordionGroup>

## Reading auto-categorization debug logs

When auto-categorization runs, Sure writes structured entries to the debug log under the `auto_categorization` category. Go to **Settings → Debug** and filter by `auto_categorization` to see them.

<AccordionGroup>
  <Accordion title="What entries will I see?">
    Each run can produce the following entries:

    - **AI categorization cache used** (info) — logged when some transactions in the batch already have an AI-set category that matches their current category. Those transactions are skipped to avoid redundant API calls. The entry includes the IDs of the cached transactions.
    - **AI categorization blocked by enrichment protection** (info) — logged when some transactions have a locked `category_id` attribute that was not set by AI. Those transactions are protected from being overwritten. The entry includes the IDs of the blocked transactions.
    - **AI categorization failed: no categories available** (error) — logged when the family has no categories configured. Auto-categorization cannot run without categories to map against.
    - **AI categorization completed** (info) — logged at the end of a successful run. The entry includes the requested transaction IDs, which transactions were categorized, which were cached or blocked, and the total number of modified transactions.
  </Accordion>

  <Accordion title="Why are some transactions not being categorized?">
    Check the debug log for `auto_categorization` entries. Transactions may be skipped because:

    - They already have an AI-assigned category that matches the current value (cache hit — shown in the **cache used** entry).
    - Their `category_id` attribute is locked by a non-AI source (shown in the **blocked** entry).
    - The family has no categories set up (shown in the **no categories available** error entry).
  </Accordion>
</AccordionGroup>

## Why is Sure not running auto-categorization and merchant detection on the same transactions again?

Sure caches AI-generated results to avoid redundant API calls and costs. Once a transaction has been processed by AI rules, it won't be re-processed unless you explicitly reset the AI cache.

<AccordionGroup>

  <Accordion title="Why does Sure cache AI results?">

    When AI rules process transactions, Sure stores:

    - **Enrichment records** - Which attributes were set by AI (category, merchant, etc.)
    - **Attribute locks** - Prevents rules from re-processing already-handled transactions

    This caching ensures:

    - Transactions aren't sent to the LLM repeatedly
    - API costs are minimized
    - Processing is faster on subsequent rule runs

  </Accordion>

  <Accordion title="How do I force Sure to re-process transactions?">

    To have AI rules re-process transactions, you need to reset the AI cache:

    1. Go to **Settings** → **Rules**
    2. Click the menu button (three dots)
    3. Select **Reset AI cache**
    4. Confirm the action

    After resetting, the next time rules run (either manually or during a sync), AI will re-process all transactions.

    **Note:** This will incur API costs if using a cloud provider.

    The reset runs in the background. You can track its progress and see how many AI cache entries were removed in **Settings → Debug**, filtered by the `ai_cache_reset` category. Each run logs when it starts, how many entries were removed per scope, and any records that could not be cleared.

  </Accordion>

  <Accordion title="When should I reset the AI cache?">

    Common scenarios for resetting the cache:

    - **Switching LLM models** - Different models may produce better categorizations
    - **After system updates** - New versions may have improved prompts
    - **Fixing miscategorizations** - When AI made systematic errors
    - **Testing** - During development or evaluation of AI features

    The AI cache is automatically cleared when you change the OpenAI model setting.

  </Accordion>

  <Accordion title="How do I verify the reset actually ran?">

    The reset runs as a background job. You can confirm it completed — and see a breakdown of how many AI cache entries were removed — in the debug log:

    1. Go to **Settings** → **Debug**
    2. Filter by category **`ai_cache_reset`**

    You will see:
    - An **info** entry when the reset is enqueued from the rules page
    - An **info** entry when the job starts on a worker
    - A **completion** entry with the number of enrichments deleted, broken down by scope
    - **warn** entries for any individual records that could not be cleared
    - An **error** entry if the job could not be enqueued at all

    If you see the enqueue entry but no start entry, the job never reached a worker — check that your worker container is running.

  </Accordion>

</AccordionGroup>

## Drawer close button missing on mobile, or two Customize buttons visible on the dashboard

On mobile, certain drawers (transactions, trades, transfers, holdings, and valuations) showed no close button because the responsive close button was configured to appear only at large screen widths. On the dashboard, the desktop Customize button appeared alongside the mobile button because `hidden` was not overriding the component's `inline-flex` display.

<AccordionGroup>
  <Accordion title="What caused these issues?">
    The design system's button component (`DS::Buttonish`) applied `inline-flex` through its icon-only container classes. Because `inline-flex` wins over `hidden` in the generated CSS, a button marked `hidden lg:inline-flex` for responsive hiding remained visible at every width rather than hiding on smaller screens.

    For drawer close buttons, `DS::Dialog#close_button` was configured as `hidden lg:flex` under the responsive option. The close button was therefore unavailable on phones.
  </Accordion>

  <Accordion title="How was it fixed?">
    The button component now lets a `hidden` class override only the display utility. Alignment and gap classes are preserved so buttons continue to lay out correctly once they become visible. Icon-only sizes no longer add `inline-flex` back through their container classes.

    `DS::Dialog#close_button` now shows at every width so drawers always have a close control on mobile.

    Upgrade to a build containing [Sure PR #4342](https://github.com/we-promise/sure/pull/4342). As of October 21, 2026, the fix is on `main` but is not in the latest stable release, `v0.7.5-hotfix.2`. No configuration change is required.
  </Accordion>
</AccordionGroup>
